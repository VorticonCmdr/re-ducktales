# Recurring destination program

The browser now runs the destination caller without requiring an external make
for every read. It flushes the table at original overlay2:1e2e, restores the
320×32 footer, draws four icons (five when atomic transport is available), then
calls the shared system/ordinary reader at1e89. Neutral and nonhorizontal inputs
still draw the selector/numbers, flip, wait0/1 and begin the next flush/draw/read.
Horizontal changes retain their sound and wait0/7; Fire takes precedence, then
flips, flushes, waits0/7 and returns. The original integer comparisons and reader
implementation are unchanged.

Physical makes/repeats/releases only update IRQ flags. An early make can be lost
at the next flush; a fresh make during drawing can be consumed at its later
reader. Buttons supply an ordinary make/break, too. No production typematic
clock or retries are invented. System keys arriving before a flush are discarded;
those arriving during drawing are handled by the shared reader afterwards.
Pause and cancelled Quit suspend that pending source call, then resume it after
the system dialog's own waits and flush. Neutral page flips do not flash the
HTML status or disable its controls;this presentation state is distinct from
the source reader window. Modifier and complete BIOS-queue
behavior remain outside the ordinary subset.

`DestinationWaits` retains the already-read-byte component contract. Conditional
fixtures initialize `Game` with its `boundary` provider; the browser explicitly
chooses `destinationInput: "keyboard"` and `DestinationLoop`. The boundary
provider is not a production demo or fallback. Calling an explicit
`destination-read` on the autonomous provider is an error. The simulation uses
injected elapsed time, driver counts and retraces; rendering never decides a
read or drawing deadline.
